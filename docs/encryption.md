# Encryption deployment and recovery

CogniStore defaults to `COGNISTORE_SECURITY_PROFILE=production`. The production
profile rejects plaintext data transports, requires certificate verification,
and checks current operator attestations before using storage whose encryption
cannot be guaranteed by the native cloud service. Invalid profile names fail
closed. `development` is an explicit exception for isolated tutorials, emulators,
and synthetic tests; the checked-in Docker Compose services select it explicitly.
The `cognistore-sample load` and `serve` commands require this explicit
development profile.

This implements the application configuration controls for ticket #60. The
application does not provision disk encryption, create KMS keys, encrypt SQLite
pages itself, or discover whether an underlying mount is encrypted. An
attestation records an operator's evidence of external controls. Passing a
configuration check is not independent proof that disks or backups are encrypted.

## Deployment configuration

Start with [the driver example](../examples/drivers.production.yaml) and
[the attestation example](../examples/encryption.production.json). Replace every
example resource, owner, evidence reference, and expiry with reviewed deployment
values. Restrict configuration writes to trusted operators and mount private
keys and credentials as runtime secrets.

```bash
export COGNISTORE_SECURITY_PROFILE=production
export COGNISTORE_DRIVERS=/etc/cognistore/drivers.yaml
export COGNISTORE_ENCRYPTION_CONFIG=/etc/cognistore/encryption.json
export COGNISTORE_TLS_CA_FILE=/etc/cognistore/pki/trusted-ca.pem
export COGNISTORE_CATALOG_DB='postgresql://cognistore@catalog.example.com/cognistore?sslmode=verify-full&sslrootcert=/etc/cognistore/pki/trusted-ca.pem'
export COGNISTORE_NATS_URL=tls://queue.example.com:4222
export COGNISTORE_API_TLS_CERTFILE=/run/secrets/api-cert.pem
export COGNISTORE_API_TLS_KEYFILE=/run/secrets/api-key.pem
export COGNISTORE_HEALTH_TLS_CERTFILE=/run/secrets/worker-health-cert.pem
export COGNISTORE_HEALTH_TLS_KEYFILE=/run/secrets/worker-health-key.pem

python -m cognistore.encryption
cognistore-api --host 0.0.0.0 --port 8443
```

The CA file is optional when the installed trust store already trusts the
services. A custom bundle must contain the needed trust chains; it is not a
certificate-verification bypass. Use workload identity or the
[runtime secret providers](secrets.md) for credentials. Configure
[authentication](authentication.md) and [authorization](authorization.md)
separately: TLS alone does not assign application permissions.

### Transport controls

| Path | Production requirement | Operator responsibility |
| --- | --- | --- |
| REST API listener | `--tls-certfile` and `--tls-keyfile`, or the two API TLS environment variables above | Provide a valid certificate chain and matching private key; use HTTPS clients. A reverse proxy must also use HTTPS upstream. |
| Worker health listener | `COGNISTORE_HEALTH_TLS_CERTFILE` and `COGNISTORE_HEALTH_TLS_KEYFILE` | Configure HTTPS readiness, liveness, and metrics clients with the correct trust bundle and hostname. |
| Python SDK | Verified `https://` API URL | Install the API's trusted CA; production SDK clients reject plaintext base URLs. |
| PostgreSQL catalog | `sslmode=verify-full` (applied when omitted), a server host, and trusted CA configuration | Issue a certificate for the configured hostname and configure server TLS. Explicit `disable`, `allow`, `prefer`, `require`, and `verify-ca` do not satisfy this policy. |
| NATS queue | `tls://` endpoints, a verified TLS context, and TLS-first handshake | Enable `handshake_first: true` on every broker; provide valid certificates for seed and advertised/discovered hosts. Configure TLS independently for cluster routes, gateways, and leaf links. |
| S3, Azure Blob, GCS | Verified HTTPS; plaintext emulators require `development` | Maintain trusted service certificates and reject plaintext at the service/network boundary. |

For PostgreSQL, `verify-full` verifies both the trust chain and server identity;
`sslrootcert` and `PGSSLROOTCERT` select libpq's CA file. See the
[PostgreSQL TLS reference](https://www.postgresql.org/docs/current/libpq-ssl.html).
NATS configures TLS separately for each connection type. A broker's client TLS
setting does not cover inter-broker traffic; use the
[NATS encryption guide](https://docs.nats.io/learn/security/encryption).

An example broker client-listener fragment is:

```text
tls {
  cert_file: "/run/secrets/queue-cert.pem"
  key_file: "/run/secrets/queue-key.pem"
  ca_file: "/etc/nats/trusted-ca.pem"
  handshake_first: true
}
```

Apply server-side policies to prevent other clients from bypassing these
requirements. Use encrypted or inaccessible diagnostic endpoints where they
could expose production telemetry. CogniStore's client checks cannot secure
traffic generated by unrelated tools or broker replication links.

### At-rest coverage

The attestation JSON uses `version: 1` and a `components` object. Every supplied
entry has exactly `mode`, `owner`, `evidence`, `expires_at`, and `rotation_days`.
Modes are `provider-managed` and `encrypted-volume`. Owner and evidence must be
nonempty strings, expiry must include a timezone, and rotation days must be a
positive integer. Production access requires unexpired evidence for the
component being used. Rotation days records policy; it does not schedule a key
rotation or renew an attestation.

| Component | Evidence must cover |
| --- | --- |
| `catalog` | Persistent PostgreSQL/SQLite data, WAL/journals, replicas, snapshots, exports, and backups. In-memory test catalogs have no persistent catalog volume. |
| `queue` | Every JetStream data directory, replica, stream snapshot, and backup. Use the provider's encryption or encrypted volumes and retain required recovery keys. |
| `storage` | All POSIX tiers and every custom S3/Azure/GCS endpoint, including bucket metadata, snapshots, replicas, and backup destinations. |
| `runtime` | Scheduler SQLite state, keyword/vector-related local files, consistency reports, spool/staging files, temporary directories, swap, and snapshots of these volumes. |

There is one attestation per component, not per tier or mount. Its evidence
reference must inventory all covered resources and their controls. Use encrypted
volumes for persistent local paths and `TMPDIR`, or memory-backed temporary
storage with encrypted/disabled swap. Backups inherit protection only if their
destination and export process preserve it. An encrypted source volume does
not encrypt a file copied to a different plaintext volume.

Native AWS S3, Azure Blob, and GCS service endpoints use provider encryption at
rest and do not need a separate `storage` attestation merely to use that native
backend. Custom endpoints still require it. Production examples can request
specific provider encryption options:

| Driver | YAML options | Meaning |
| --- | --- | --- |
| S3 | `server_side_encryption: AES256` | Request SSE-S3 for new uploads. |
| S3 | `server_side_encryption: aws:kms` with `kms_key_id` | Request the selected KMS key for new uploads, including multipart initiation. |
| Azure Blob | `encryption_scope` | Select a pre-provisioned encryption scope for writes. |
| GCS | `kms_key_name` | Select a pre-provisioned Cloud KMS key for uploads. |

AWS documents [S3's default and requested server-side encryption](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-encryption.html).
Azure documents [storage encryption at rest](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption),
and Google documents [standard Cloud Storage encryption](https://docs.cloud.google.com/storage/docs/encryption/default-keys).
Provider-managed defaults do not prove that a historical object inventory meets
an organization's stronger customer-managed-key policy. Verify that inventory
and the configured key permissions before admitting production data.

### Safe configuration status

```bash
python -m cognistore.encryption
cognistore --no-config encryption-status --json
# Optionally inspect configured driver modes as well:
cognistore --drivers /etc/cognistore/drivers.yaml encryption-status --json
```

Both forms report the selected profile, TLS requirements and custom-CA presence,
plus each component's attestation mode, source, currency, and rotation interval.
It omits owners, evidence references, resource identifiers, credentials, keys,
and file paths. `unattested` means no entry was supplied; it can be expected for
unused components or a storage-only native-cloud deployment. The module command
and CLI without a resolved driver configuration stay offline. When `--drivers`
is selected directly or through CLI configuration, the CLI creates those clients
and resolves any credential references, so it can contact credential providers.
It also reports each tier's safe mode, source, and `key_configured` flag. Neither
form inspects volumes or validates a deployed API's certificate. Validate service
access and external controls as separate deployment evidence.

For SDK, JWT, Vault, and placement clients, programmatically supplied HTTPX
clients/transports must retain certificate and hostname verification, including
proxy/mounted transports. Production rejects disabled verification and custom
transports whose TLS settings cannot be inspected; `MockTransport` remains
available for offline tests. SDK requests reject redirects even when an
injected client enables them.

## Key ownership and rotation

Assign a named operations team to each component. Record the provider, key
policy, rotation interval, resource inventory, recovery permissions, and backup
retention in its evidence record. Grant workloads only the encrypt/decrypt
permissions needed for their resources; retain key administration and deletion
authority with the key owner. Do not put raw keys in driver or attestation files.

For provider or volume key rotation:

1. Provision the new key/version and verify workload and recovery identities can
   use it. Preserve the previous version while readers, active transfers, and
   retained backups still depend on it.
2. Update the service encryption configuration or the driver's key/scope
   reference, then recreate affected clients/workers through a rolling restart.
   Changing an upload option only affects new writes; it does not rewrite old
   objects or backups. Use the provider's supported re-encryption procedure
   when a policy requires rewriting existing data.
3. Write/read a synthetic object, verify its checksum and provider encryption
   metadata, and read an object written before rotation. Check multipart paths
   when those are used. Restore a retained backup using its original key version.
4. Record results and renew the attestation after review. Retire old key
   versions only after every dependent object, replica, snapshot, and backup
   has expired or has been re-encrypted and restored successfully.

For TLS certificate and CA rotation, distribute an overlapping old/new CA bundle
first, restart clients so they load it, deploy the new leaf certificate and key,
and verify every hostname and reconnect path. Then remove old trust and restart
clients after all services have rotated. Changing a PEM file does not update
an already-created SSL context. Do not disable certificate validation to bridge
a failed rotation; restore the valid certificate/trust pair and investigate.

## Backup and recovery exercises

Back up the catalog with a database-supported consistent snapshot procedure and
the queue with its supported snapshot/backup procedure. Store backup data,
manifests, and any intermediate exports on encrypted destinations; use verified
TLS for transfer. Keep key material in the key service or a separately protected
recovery mechanism, not alongside a plaintext export. Record the backup digest,
timestamp, key version reference, schema/version, and recovery permissions in
restricted evidence. An ordinary SQLite file copy while writes are active is
not a substitute for a consistent online backup.

Perform a deployment drill before accepting production data, and after relevant
key, certificate, storage, or backup changes:

1. Inventory catalog, queue, tier, runtime, replica, and backup encryption using
   provider configuration or host volume-management evidence. Check every
   resource named by each attestation.
2. Exercise verified PostgreSQL, NATS, storage, and API connections. Demonstrate
   rejection of plaintext, untrusted certificates, wrong hostnames, and a
   discovered/reconnect queue endpoint lacking valid TLS.
3. Rotate a certificate and a storage key with overlapping trust/access. Retain
   old-version data and confirm new and existing objects remain readable.
4. Restore catalog, object, and queue backups into isolated encrypted resources.
   Confirm catalog schema and placements, object checksums, and queue recovery;
   test both the current and a retained pre-rotation backup.
5. Record timestamps, environment/version, control evidence, successful checks,
   negative checks, and recovery durations. Renew the reviewed attestations and
   alert before their expiry. Destroy only the disposable drill resources.

The reproducible offline application drill is:

```bash
python -m pytest -q tests/unit/test_encryption_recovery.py
```

Recorded offline execution: 2026-09-18, CPython 3.12.2 on macOS, **2 passed**.
No live cloud, broker, or physical-volume validation was performed by that run.

It performs real loopback TLS handshakes using ephemeral certificates, proves
old/new CA overlap, rejects wrong hosts and retired/untrusted CAs, and restores
a consistent SQLite online snapshot through the production catalog DAL. Missing
or expired catalog evidence must block the restore's catalog open. The fixture's
temporary directory stands in for an approved volume; the drill does not prove
that the host filesystem is encrypted. Driver contract tests also inspect the
configured provider encryption options. These offline exercises do not replace
the live deployment, cloud KMS, encrypted-volume, or queue-backup drill above.
