# M1 implementation review — 2026-08-20

This review reconciles the current `main` implementation with the M1 backlog,
records validation evidence, and identifies work that must be completed before
M1 can be considered reliable. GitHub Issues remains the source of truth; the
local [`tickets.md`](tickets.md) mirror was refreshed on 2026-08-22.

## Outcome

The completed immediate-priority work is substantial and well tested. Tickets
#17, #18, #20 through #25, and #27 have implementation and test evidence for
all 36 of their written acceptance criteria. The merged tree includes S3 and
POSIX conformance, NATS JetStream workers, safe previews, bounded streaming,
destination integrity checks, durable move state, retries and dead letters,
per-tier throughput controls, packaging, and CI quality gates.

M1 is **not release-ready** because the remaining delivery work has not been
completed. The two critical cleanup races found by this review were resolved
on `fix/critical-movement-races` with durable generation tokens, conditional
source deletion, catalog reconciliation, and synchronized regressions.

## Critical findings

### BUG-2026-001 — A move can delete a newer source generation

Severity: **S0 (Critical)**

Status: **Fixed on `fix/critical-movement-races`.** Move jobs now persist the
source generation, POSIX and S3 expose conditional generation-aware deletion,
and cleanup retains a replacement source and reconciles the catalog to it.

The mover hashes the source bytes during transfer, verifies the destination,
commits the destination placement, re-verifies only the destination, and then
deletes the current source key. It does not persist or conditionally check the
identity of the source generation being moved.

A source overwrite between transfer and cleanup therefore produces this
sequence:

1. The old source bytes are transferred and verified at the destination.
2. Another writer replaces the source key with new bytes.
3. Cleanup verifies the old destination bytes.
4. Cleanup deletes the source key, which now names the new version.
5. The move reports success and the catalog points to the old destination.

A controlled POSIX reproduction on commit `fe9cd16` returned
`result_verified=True`, retained `b"old-version"` at the destination, deleted
the newer source, and recorded the destination tier in the catalog.

Relevant implementation:

- Source transfer and hash: `cognistore/core/mover.py`, `_resume`, PREPARED phase.
- Destination verification: `cognistore/core/mover.py`, TRANSFERRED phase.
- Unconditional source deletion: `cognistore/core/mover.py`, CLEANUP phase.

Implemented resolution:

- Bind every move job to a stable source generation or version token.
- Add a driver contract for conditional, generation-aware deletion.
- Abort cleanup and retain the source when its generation no longer matches.
- Define catalog behavior when a new source generation appears after placement
  commit.
- Add POSIX and S3 regressions for replacement during transfer, after initial
  verification, after catalog commit, and immediately before cleanup.

### BUG-2026-002 — The destination can change after final verification

Severity: **S0 (Critical)**

Status: **Fixed on `fix/critical-movement-races`.** The verified destination
generation is persisted, rechecked at cleanup, and covered by a regression
that replaces the destination after final verification. A mismatch retains
the source, fails the job with evidence, and restores the source placement.

Cleanup verifies the committed destination and then deletes the source in two
separate backend operations. No immutable destination version is pinned across
that boundary. A writer can therefore replace the destination after the final
verification but before source deletion.

A controlled threaded POSIX reproduction paused immediately after final
destination verification, replaced `b"good-version"` with `b"evil-version"`,
and resumed cleanup. The move returned `result_verified=True`, deleted the
source, retained the unverified destination, and left the catalog checksum for
the former good bytes.

Implemented resolution:

- Persist immutable source and destination version tokens in the move job.
- Make cleanup conditional on both versions still matching the verified move.
- Retain the source and move job evidence on any mismatch.
- Add a race regression that changes the destination at the final
  verification/delete boundary for POSIX and S3.

Both critical races are now covered by generation-aware conditional operations
and object-level coordination in the POSIX driver.

## High-severity findings

The audit tracked six S1 issues in `bug_tracker.md`. Four correctness blockers
were fixed on `main`; two product gaps remain open:

- **BUG-2026-003 — POSIX durability barriers were missing (fixed).** POSIX
  publication and deletion now fail closed around file and directory sync
  barriers, with Darwin `F_FULLFSYNC` support and recovery coverage.
- **BUG-2026-004 — Catalog scans publish misleading checksums and replace
  metadata.** Objects larger than 1 MiB receive a first-megabyte digest under
  `sha256`, and the scan overwrites existing metadata rather than merging
  namespaced scan evidence.
- **BUG-2026-005 — Manual moves are not operably resumable.** The CLI neither
  accepts an idempotency key nor exposes move recovery/status. A crash after
  destination publication makes the next invocation fail on collision.
- **BUG-2026-006 — One bad recovery job starved later jobs (fixed).** Recovery
  now terminalizes a definitively missing source, continues later jobs, and
  reports the terminal failure after the batch.
- **BUG-2026-007 — Scans could corrupt placement during active moves (fixed).**
  Generation-stable observations and object-specific move fences now make
  catalog publication move-aware and atomic.
- **BUG-2026-008 — SQLite prefixes expanded wildcards and ignored case
  (fixed).** SQLite now uses literal, binary prefix matching consistent with
  the in-memory catalog.

## Additional gaps and tracking corrections

### Manual moves are not operably resumable

`Mover.move()` supports explicit idempotency keys, but the `move` CLI does not
expose one and generates a new random key on every invocation. After a crash
that publishes the destination, a repeated manual command encounters a
destination collision instead of resuming the durable job. Add a CLI
idempotency key, move status/list/resume commands, and documented recovery.
This fits naturally into ticket #26.

### POSIX containment is check-then-use

The POSIX driver rejects paths containing symlinks when it validates them, but
later uses ordinary path-based open, link, replace, stat, and unlink calls. A
concurrent directory-to-symlink swap can invalidate the earlier containment
decision. Either use descriptor-relative no-follow operations or explicitly
document and enforce a trusted, non-mutating tier-root threat model.

### Catalog scan checksums are sample checksums

Catalog scans read at most the first 1 MiB and store its digest under the
generic `sha256` metadata key. For larger objects that value is not the full
object checksum and can be confused with the verified placement checksum.
Rename it to make the sampled scope explicit until ticket #34 introduces
canonical full-object checksums.

Move-aware scan coordination was added on 2026-08-21. Canonical full-object
checksums and metadata provenance remain open under BUG-2026-004 and ticket
#34.

Validation/process gaps:

- `docker compose config` fails because `docker-compose.yml` is empty; this is
  open ticket #28.
- The performance harness is empty and no #29 scale evidence exists.
- `ruff format --check` currently reports 49 files and is not a CI gate. Either
  standardize formatting or explicitly document lint-only Ruff usage.
- Auditing all tools installed in an arbitrary local virtual environment is
  environment-dependent; unpinned bootstrap packages can fail `pip-audit
  --local` even when project dependencies pass. CI should audit a reproducible
  lock or constraints set rather than incidental environment tooling.
- The existing workspace `.venv` produced a `readline` import segmentation
  fault during one validation path. Healthy Python installations passed every
  suite, so recreate that virtual environment before relying on it locally.
